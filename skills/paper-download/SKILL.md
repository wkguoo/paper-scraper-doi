# Paper Download

Use this as the single entry point for a mixed DOI/title paper list. Run the
project workflow first. Zotero handles only rows remaining in
`zotero_fallback.csv`; never send the complete input list to Zotero again.

## Repository and prerequisites

Locate the repository in this order:

1. Current directory or a parent containing `paper_batch.py`,
   `sd_institutional_skill.py`, `paper_skill.py`, and `paper_automation`.
2. `$env:PAPER_SCRAPER_DOI_ROOT` when it points to that repository.
3. A packaged folder containing the same scripts.
4. Otherwise ask the user for the repository path.

Use `.venv\Scripts\python.exe` when present. The Zotero stage requires Zotero
to be open and connected to Codex. Never expose cookies, passwords, or session
data, and never automate a CAPTCHA.

## CSV reading contract

Read `manual_retry.csv`, `zotero_fallback.csv`, and any existing Zotero result
file with Python `csv` semantics, `newline=""`, and `encoding="utf-8-sig"`
(UTF-8-SIG). Require the exact header generated by the project. The two pending
files use this header, in this order:

```text
task_id,source_index,input_doi,input_title,doi,title,authors,journal,year,publisher,status,source,file,reason
```

Every `zotero_results*.csv` file uses exactly:

```text
task_id,zotero_item_id,attachment_path,status,reason
```

A completely blank record has no non-whitespace value in any parsed field and
is ignored. A record is a data row when at least one field is non-empty after
trimming. If decoding, CSV parsing, field count, or exact header validation
fails, stop and report the error; do not guess or continue.

## Batch protocol

Keep the CLI's printed run directory as `<run-dir>`. Do not edit the original
input or any project-generated pending CSV.

1. Run the project workflow first:

   ```powershell
   .\.venv\Scripts\python.exe paper_batch.py start --input "papers.xlsx" --out "results"
   ```

2. Read `<run-dir>\working\manual_retry.csv` using the CSV contract above. If
   it contains data rows, pause once for the user to finish the required
   browser action, then run exactly one retry:

   ```powershell
   .\.venv\Scripts\python.exe paper_batch.py resume --run-dir "<run-dir>"
   ```

   Never run `paper_batch.py resume` a second time. If there are no data rows,
   skip resume.

3. After that one permitted retry, read
   `<run-dir>\working\zotero_fallback.csv` with the same CSV rules. If it has
   no data rows, create a header-only Zotero result file by the result-file
   recovery rules below, then run:

   ```powershell
   .\.venv\Scripts\python.exe paper_batch.py finalize --run-dir "<run-dir>" --zotero-results "<selected-zotero-results.csv>"
   ```

4. If fallback data rows remain, check Zotero availability with
   `library_search(entity:"libraries", mode:"list")` before any write.

5. Resolve one library for the entire attempt. Use only the active personal
   library selected by the current Codex Zotero scope. If the list does not
   uniquely identify that active personal library, ask the user once to choose;
   do not guess a group library. When the scope already provides a clear
   `libraryID`, keep it. After selection, every search and write in this attempt
   must use the same `libraryID`.

6. Create and preserve one temporary collection with this exact call:

   `collection_update(action:"create", name:"Codex下载回退_YYYYMMDD_HHMMSS", libraryID:<libraryID>)`

   Capture the returned `collectionId`. Keep this collection and all its items
   after the task.

7. Resolve every fallback item before requesting PDFs:

   - Normalize each DOI by trimming whitespace, removing a DOI URL or `doi:`
     prefix, and casefolding. Search every DOI before any import with:

     `library_search(entity:"items", mode:"search", text:"<normalized DOI>", include:["metadata","attachments"], libraryID:<libraryID>)`

   - Batch-add existing items to the temporary collection with exactly:

     `library_update(kind:"collections", action:"add", assignments:[{itemId:<id>, targetCollectionId:<collectionId>}, ...], libraryID:<libraryID>)`

   - De-duplicate DOI values that were not found, then import only those missing
     identifiers in one batch:

     `library_import(kind:"identifiers", identifiers:[...], targetCollectionId:<collectionId>, libraryID:<libraryID>)`

     After import, use returned item IDs only when the response unambiguously
     maps them to the DOI; otherwise repeat the exact DOI search and confirm the
     item ID. Never import an already-found DOI.

   - For a row without DOI, search its normalized title with:

     `library_search(entity:"items", mode:"search", text:"<normalized title>", include:["metadata","attachments"], libraryID:<libraryID>)`

     Normalize title text with Unicode NFKC, then `casefold`. Replace each run
     of Unicode whitespace, punctuation, or symbol characters with one ASCII
     space, collapse repeated spaces, and trim. Accept a candidate only if the
     normalized titles are exactly equal and either the same four-digit year or
     the first author also matches. For first author, prefer the structured
     family name; when unavailable use the complete first creator string, then
     apply the same text normalization. If title, year, or first-author evidence
     cannot be compared reliably, write `metadata_uncertain`; do not import or
     guess an item ID.

   Confirm collection creation, item assignments, identifier import, and tags
   by batch, never once per paper.

8. Detect existing PDF attachments for all resolved items. For a valid existing
   PDF, generate `existing_pdf` and do not request another. For all remaining
   item IDs, make one `zotero_script(mode:"write")` call for the entire batch.
   Keep the compatibility guard and undo step exactly as follows:

   ```javascript
   const createdIds = [];
   env.addUndoStep(async () => {
     for (const id of createdIds) {
       const attachment = await Zotero.Items.getAsync(id);
       if (attachment && !attachment.deleted) await attachment.eraseTx();
     }
   });
   if (typeof Zotero.Attachments.addAvailablePDF !== "function") {
     return { ok: false, reason: "zotero_api_unavailable", rows: [] };
   }
   const rows = [];
   for (const itemId of itemIds) {
     const item = await Zotero.Items.getAsync(itemId);
     let attachment = null;
     for (const attachmentId of item.getAttachments()) {
       const candidate = await Zotero.Items.getAsync(attachmentId);
       if (candidate.isPDFAttachment() && await candidate.fileExists()) {
         attachment = candidate;
         break;
       }
     }
     let status = "existing_pdf";
     if (!attachment) {
       attachment = await Zotero.Attachments.addAvailablePDF(item);
       status = attachment ? "downloaded" : "no_pdf";
       if (attachment) createdIds.push(attachment.id);
     }
     rows.push({
       itemId,
       status,
       attachmentPath: attachment ? attachment.getFilePath() : "",
       reason: attachment ? "" : "no_available_pdf",
     });
   }
   return { ok: true, rows };
   ```

   Each item without an existing PDF is included in this call once. If the
   compatibility guard fails, generate `zotero_api_unavailable` for the
   affected resolved items and never report a download.

9. Write result rows using the result-file recovery rules below. A non-empty
   `attachment_path` must be an absolute Windows path to an existing ordinary
   PDF file. Reject relative paths, directories, reparse points, and non-PDF
   files; generate `no_pdf` with a precise reason instead.

10. Apply result tags in one or two batch calls. Success uses exactly:

    `library_update(kind:"tags", action:"add", assignments:[{itemId:<id>, tags:["codex-download-success"]}, ...], libraryID:<libraryID>)`

    Failure uses exactly:

    `library_update(kind:"tags", action:"add", assignments:[{itemId:<id>, tags:["codex-download-failed"]}, ...], libraryID:<libraryID>)`

    Add the failed tag only to failed rows that actually have an `itemId`.
    Rows such as `metadata_uncertain` or `zotero_unavailable` with no item ID
    must not produce a tag assignment.

11. Run `paper_batch.py finalize` exactly once for the selected result file:

    ```powershell
    .\.venv\Scripts\python.exe paper_batch.py finalize --run-dir "<run-dir>" --zotero-results "<selected-zotero-results.csv>"
    ```

    `finalize` non-destructively copies accepted PDFs into `<run-dir>\pdfs\`.
    It must not overwrite existing output; filename conflicts use the project's
    reconcile rules. Never move, rename, delete, or modify a Zotero attachment.

## Result-file recovery rules

- This protocol generates only these six statuses: `existing_pdf`,
  `downloaded`, `metadata_uncertain`, `zotero_unavailable`,
  `zotero_api_unavailable`, and `no_pdf`.
- The project parser also accepts `not_found`, `no_attachment`, and
  `download_failed` for compatibility with other adapters. Codex does not
  actively generate those three compatibility statuses in this protocol.
- For the first result write, use exclusive creation of
  `<run-dir>\working\zotero_results.csv`. Never overwrite or append.
- If that canonical file already exists, validate its exact header and require
  its nonblank `task_id` set to equal the current task IDs before reuse. Reject
  malformed or duplicate IDs. If the header is valid but the ID set is stale
  or incomplete, create a new timestamped retry file for the current IDs;
  never overwrite or append to the canonical file.
- If Zotero is unavailable and no canonical file exists, exclusively create it
  with one `zotero_unavailable` row per current fallback task, then pass it to
  finalize. If a valid canonical file has exactly the current task IDs, it may
  be finalized as immutable prior evidence. If the IDs differ, exclusively
  create a timestamped retry file with the current `zotero_unavailable` rows.
- Zotero-unavailable finalize is a report update, not success. The CLI must say
  `批次未完成且可恢复`, show the unresolved count and final PDF directory, and
  must not print a resume command.
- When Zotero later becomes available, exclusively create
  `working\zotero_results_retry_YYYYMMDD_HHMMSS.csv`, write the new current-task
  outcomes there, and pass that new file to finalize. The workflow updates
  unfinished rows by `task_id`; never replace or append to the old file.
- When fallback is empty but the canonical file already has data rows or does
  not match the current task IDs, exclusively create a header-only
  `zotero_results_retry_YYYYMMDD_HHMMSS.csv` and finalize with that timestamped
  file instead of reusing stale rows.

## Output tree

```text
results\paper_batch_YYYYMMDD_HHMMSS\
├── pdfs\
├── reports\
│   ├── final_manifest.csv
│   ├── final_manifest.xlsx
│   ├── failed.csv
│   └── run_summary.txt
└── working\
    ├── manual_retry.csv
    ├── zotero_fallback.csv
    ├── zotero_results.csv
    └── zotero_results_retry_YYYYMMDD_HHMMSS.csv
```

`pdfs\` is the final copy destination, `reports\` is the audit trail, and
`working\` contains resumable handoff files.

## ScienceDirect and open-access routes

For a ScienceDirect or Elsevier request that does not need the unified batch,
use `sd_institutional_skill.py`. For noisy beginner lists, start with
`--beginner --preflight`; formal PDF runs may produce
`supplement_download_report.csv` and `supplements\`. Add
`--no-download-supplements` only when the user explicitly wants PDFs without
supplementary files.

For open-access candidate assistance without institutional access, use
`paper_skill.py` and report unresolved rows honestly. Do not broaden the source
set beyond the project's documented routes.

## Safety

- Do not expose credentials, cookies, passwords, or session data.
- Do not automatically solve a CAPTCHA; only the one user-handled retry is
  permitted.
- Do not overwrite original inputs, result files, existing PDFs, Zotero
  attachments, collections, or items.
- Never report an unavailable or unresolved Zotero fallback as complete.
